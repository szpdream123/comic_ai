# 用户中心化作用域移除设计

**日期：** 2026-07-12
**状态：** 已完成（2026-07-13 全仓、数据库与定向回归验收通过）
**文档类型：** Diataxis Explanation + Reference
**目标：** 彻底移除 `organization`、`workspace` 及其 ID 依赖，将用户作为唯一业务归属根。

## 1. 结论

项目运行时不再保留组织和工作空间概念。最终数据库、后端、前端、契约、任务系统、权限、测试和当前有效文档中均不得继续依赖：历史审计文档可以描述已退役背景，但不能成为实现依据。

- 旧组织表、旧空间表及其衍生业务模型；
- 旧组织归属列、旧空间归属列及对应驼峰参数；
- 为兼容旧作用域生成的 UUID、默认组织或默认工作空间；
- 基于组织或工作空间的鉴权、过滤、唯一约束、索引、错误码和 API 参数。

目标模型以 `users` 为唯一根：项目由用户拥有，项目子资源通过 `project_id` 继承归属；不属于项目的个人资源直接使用 `owner_user_id`；子账户通过现有团队成员模型和显式分配关系访问主用户资源。

## 2. 目标与非目标

### 2.1 目标

1. 建立单一、可解释的用户归属模型。
2. 清除数据库中的组织和工作空间表、列、外键、索引与约束。
3. 清除运行时代码、API、消息载荷、缓存键和前端状态中的旧作用域。
4. 在不丢失业务数据的前提下完成所有权回填和切换。
5. 为后续开发提供明确规则，防止旧概念重新进入系统。

### 2.2 非目标

- 不取消主用户与子用户的团队协作能力。
- 不把所有系统级或全局配置强行归属到某个用户。
- 不借本次改造重写无关业务、改变现有功能或调整 UI 风格。
- 不继续维护组织或工作空间兼容层。
- 不在本设计阶段直接执行生产删表、删列或数据清理。

## 3. 改造前问题与处理结果

改造前，同一条数据可能同时存在用户、组织和空间三套归属解释，容易造成越权、漏过滤、异步任务错投和唯一约束冲突。当前处理结果为：

- Actor 上下文只保留用户、成员、角色与能力语义；旧兼容作用域服务及模块已删除。
- 项目创建契约和前端调用不再接收、缓存或发送旧作用域参数。
- 数据库加载器只加载用户中心化 schema baseline 与模型目录 reference seed。
- 旧增量迁移链已终止支持并从主仓库删除，新环境直接从 clean baseline 初始化。
- 正式数据库已通过 catalog 审计，旧表、旧列及关联数据库对象均为零。

## 4. 目标领域模型

```text
users (唯一业务归属根)
├── projects.owner_user_id
│   ├── 项目内容（通过 project_id 继承）
│   ├── 画布数据（通过 project_id 继承）
│   ├── 项目文件（通过 project_id 继承）
│   └── 项目任务（通过 project_id 继承）
├── 个人资源.owner_user_id
│   ├── 个人素材库
│   ├── 模型配置/凭据
│   ├── 钱包与权益
│   └── 用户级幂等记录
└── team_members
    └── 显式项目/资源分配关系

system/global records
└── 无伪造 owner_user_id，仅保留明确的系统级语义
```

### 4.1 所有权规则

1. **项目是主要聚合根。** 所有天然属于项目的记录只保存 `project_id`，不重复保存 `owner_user_id`。
2. **项目外个人资源显式归属用户。** 使用 `owner_user_id`，外键指向 `users.id`。
3. **子用户不是新的租户根。** `team_members` 表达成员身份，分配表表达其可访问的项目或资源。
4. **系统记录不伪造所有者。** 全局模型目录、系统配置、公共字典等保持系统级语义。
5. **鉴权从所有权链推导。** 先确认当前用户或成员，再根据项目所有者和分配关系判断访问权。
6. **禁止隐式默认作用域。** 不生成默认组织、工作空间或兼容 UUID。

### 4.2 前台管理员与后台管理员身份边界

本节是身份模型的强制架构约束，不是过渡兼容方案或实现建议。所有数据库结构、认证会话、授权判断、API 契约、异步任务、幂等记录和审计记录都必须遵守，任何历史实现与本节冲突时均以本节为准。

1. **前台管理员就是用户。** 前台出现的主账号管理员、团队管理员、项目管理员等身份，主体始终是 `users` 中的真实用户，只通过角色、能力和成员分配关系获得管理权限，不建立独立管理员主体，也不得绕过用户所有权链。
2. **后台管理员独立于前台用户。** 后台管理平台使用 `admin_accounts` 作为独立身份根，不要求也不得自动关联 `users`，后台登录态、角色和权限只从后台管理员账号解析。
3. **禁止后台管理员冒充前台用户。** 后台操作不得选择“第一个用户”、固定用户、随机用户或默认用户填充 `user_id`、`actor_user_id`、`created_by_user_id` 等字段；没有真实前台用户语义时这些字段必须为空。
4. **幂等作用域严格分离。** 前台用户命令使用 `user:<user_id>`，后台管理员命令使用 `admin:<admin_account_id>`，同一幂等键不得跨两类主体共享或回放。
5. **审计主体必须真实。** 前台操作记录真实 `actor_user_id`；后台操作记录真实 `actor_admin_account_id`，并保持 `actor_user_id` 为空。若操作目标属于某个用户，可记录目标 `user_id`，但不得把目标用户写成操作人。
6. **系统写入不伪造身份。** 定时任务、迁移和系统消费者没有用户或后台管理员发起者时，两个 actor 字段都为空，并通过明确的系统事件类型表达来源。
7. **禁止建立身份映射。** `admin_accounts` 不得以 `user_id` 外键、映射表或隐式约定关联 `users`，`users` 也不得保存 `admin_account_id`；后台业务记录可以把某个前台用户作为操作目标，但目标关系不能被解释为身份关系。
8. **认证与授权链路完全隔离。** 前台接口只接受前台用户会话，后台接口只接受后台管理员会话；两类 token、cookie、角色和权限不得互认、复用或在缺失主体时互相回退。

## 5. 数据域迁移矩阵

| 数据域 | 当前遗留影响 | 目标结构 | 迁移动作 |
| --- | --- | --- | --- |
| 身份与访问 | ActorContext 携带组织/工作空间 | `userId`、可选 `teamMemberId`、角色与授权能力 | 删除旧字段和解析逻辑，改为用户/成员上下文 |
| 项目与内容 | 项目或内容按旧作用域过滤 | `projects.owner_user_id`；子内容只关联 `project_id` | 回填项目所有者，删除子表冗余作用域列 |
| 画布 | 画布、节点、快照可能带旧作用域 | 画布归项目，节点/快照归画布或项目 | 用项目链鉴权并删除旧列 |
| 存储与素材库 | 对象键、文件记录按 workspace 分区 | 项目文件按 `project_id`；个人素材按 `owner_user_id` | 迁移元数据与对象键，保留旧键读取过渡期 |
| 工作流与模型网关 | 请求、运行、凭据记录带旧作用域 | 项目运行归 `project_id`；个人配置归 `owner_user_id` | 修改任务载荷、幂等键、配额查询和日志字段 |
| 成员与权益 | 旧 memberships/organization entitlements | 用户订阅、用户权益、团队成员授权 | 回填用户权益并删除旧成员/权益表 |
| 积分 | 组织钱包或旧作用域账本 | 用户钱包与用户账本 | 以用户为账户根，校验余额守恒 |
| 支付 | 订单、订阅关联组织 | 订单和订阅关联购买用户 | 回填购买者，重建用户级唯一约束 |
| 团队与子账户 | 组织成员、工作空间角色 | `team_members` + 显式 assignment 表 | 保留团队能力，删除租户含义和旧角色映射 |
| 审计/Outbox/幂等/后台 | 日志、事件、键值含旧 ID | 使用 `actor_user_id`、`owner_user_id`、`project_id` 或系统语义 | 修改事件 schema、查询条件、缓存键和后台筛选 |

## 6. 删除对象清单

### 6.1 删除整表

完成数据迁移和引用清零后删除：

- `organizations`
- `workspaces`
- 旧 `memberships`
- `organization_entitlements`
- `organization_membership_subscriptions`
- `team_plan_limits`
- 已被 `team_members` 与新分配模型替代的旧团队 group/profile/assignment/ownership/adjustment 表

最后一组表必须先按实际 schema 建立精确清单；任何仍承载唯一业务数据的表不得直接删除，应先迁移到用户、团队成员或项目模型。

### 6.2 删除字段及数据库对象

- 所有表中的旧组织归属列和旧空间归属列；
- 相关外键、唯一约束、检查约束和触发器；
- 以旧字段开头或包含旧字段的单列、复合和部分索引；
- 数据库函数、视图、物化视图、RLS policy 中的旧引用；
- seed、fixture 和基线迁移中的旧作用域初始化。

## 7. 运行时改造

### 7.1 ActorContext

目标上下文只表达真实身份和授权信息：

```ts
type ActorContext = {
  userId: string;
  teamMemberId?: string;
  roles: string[];
};
```

具体字段以现有公共接口为准，但不得保留旧组织或空间参数及兼容 scope。所有服务应接收用户、项目或团队成员语义明确的参数。

### 7.2 项目 API

- 项目创建接口不接受客户端传入的旧作用域或所有者标识。
- 服务端从登录态取得主用户，并写入 `projects.owner_user_id`。
- 子用户创建或操作项目时，通过团队成员授权规则确定目标主用户，不接受客户端伪造所有者。
- 项目查询统一通过所有者或成员分配关系过滤。

### 7.3 存储作用域

- 项目文件路径和记录使用 `project_id` 作为业务分区。
- 个人素材使用 `owner_user_id`。
- 迁移期间建立旧对象键到新对象键的映射；读路径可短期双读，写路径只写新键。
- 完成访问日志确认和完整性校验后再清理旧对象。

### 7.4 异步任务与供应商请求

- 队列载荷、Outbox 事件、定时任务、模型供应商请求删除旧作用域字段。
- 项目任务携带 `project_id` 与发起者 `actor_user_id`；个人任务携带 `owner_user_id`。
- 幂等键、限流键、缓存键和追踪标签切换为用户/项目语义。
- 在旧格式消息全部消费或显式迁移前，不得删除兼容消费者。

## 8. 数据迁移方案

### 阶段 1：数据审计

1. 枚举全部表、列、索引、约束、视图、RLS、函数和触发器中的旧引用。
2. 统计每张表的总量、空值、孤儿记录、多候选所有者和无法归属记录。
3. 建立“旧记录 → 目标用户/项目”的审计表或离线报告。
4. 对所有无法唯一确定归属的数据执行硬停止，不允许猜测。

### 阶段 2：Expand

1. 为项目增加并约束 `owner_user_id`（若尚不存在）。
2. 为项目外个人资源增加 `owner_user_id`。
3. 增加新的用户/项目索引、外键和必要的分配关系。
4. 应用层开始双读校验，但新写入只使用目标字段。

### 阶段 3：Backfill

按确定性优先级批量回填，并记录每批数量、耗时和异常：

1. 已存在的直接用户外键；
2. 项目现有创建者或明确所有者；
3. 可唯一映射到用户的团队成员关系；
4. 可唯一映射到用户的历史组织/工作空间所有者；
5. 经人工确认的例外映射。

出现零候选或多候选时立即停止该记录迁移，进入人工处置清单。禁止用“第一个成员”、固定用户或随机 UUID 兜底。

### 阶段 4：Cutover

1. 所有写路径仅写用户/项目字段。
2. 所有读路径和权限判断仅使用新模型。
3. API、前端和 SDK 停止发送旧字段。
4. 监控旧字段读取、旧缓存键和旧消息格式命中率。

### 阶段 5：排空异步数据

1. 排空旧队列、Outbox、重试任务和死信队列。
2. 处理仍携带旧字段的定时任务和回调。
3. 确认旧格式消息连续一个完整保留周期为零。

### 阶段 6：Contract / Drop

1. 删除兼容服务、旧 DTO、旧事件字段和旧查询分支。
2. 删除旧索引、外键和约束。
3. 删除旧组织归属列和旧空间归属列。
4. 删除废弃表。
5. 删除数据库和对象存储中的迁移辅助映射。

### 阶段 7：清理基线迁移

全新环境直接使用不含旧概念的 clean baseline。项目当前唯一已部署数据库必须先完成数据切换，再通过完整 catalog fingerprint 登记 baseline；登记不能替代数据迁移，也不能接受未知结构。旧增量链已经 EOL，任何未来出现的未知历史 fingerprint 必须先离线审计并编写专用迁移，runner 应硬失败而不是猜测升级或自动登记。

## 9. 索引替换与性能保障

旧索引不能简单删除，必须按查询入口替换：

| 旧查询维度 | 新索引方向 |
| --- | --- |
| 旧空间主键组合 | `(project_id, id)` 或项目主键 |
| 旧组织时间范围组合 | `(owner_user_id, created_at)` |
| 组织级唯一名称 | 用户级或项目级唯一名称，按真实业务语义决定 |
| 组织/空间级幂等键 | `(owner_user_id, idempotency_key)` 或 `(project_id, idempotency_key)` |
| 组织级任务列表 | `(project_id, status, created_at)` 或 `(owner_user_id, status, created_at)` |

切换前后应对高频查询执行 `EXPLAIN (ANALYZE, BUFFERS)` 对比，并监控慢查询、锁等待、索引体积和回填对线上写入的影响。大表回填使用可恢复的小批次，不执行长事务全表更新。

## 10. 测试矩阵

| 层级 | 必测内容 |
| --- | --- |
| Schema | 新环境建库、旧环境升级、外键/非空/唯一约束、删表删列 |
| 数据迁移 | 数量守恒、所有权唯一、孤儿为零、钱包余额守恒、订单订阅归属 |
| 单元测试 | 用户/成员 ActorContext、项目所有权、分配授权、系统记录 |
| API | 创建/查询/更新项目不接收旧字段；跨用户访问拒绝 |
| 异步 | 新旧消息排空、重试、死信、幂等和回调 |
| 存储 | 新键读写、旧键迁移、跨用户隔离、清理前完整性 |
| 前端 | 请求体、状态、缓存、本地存储和路由中无旧字段 |
| 回归 | 主用户、子用户、后台管理员、支付、积分、模型调用、画布与素材库 |
| 静态门禁 | 全仓搜索和生成物扫描中旧引用为零 |

身份边界测试必须证明：前台管理员使用真实 `users.id` 完成授权；后台管理员在没有任何前台用户数据时仍可独立登录和执行授权操作；前后台会话不能互换；后台操作不产生伪造的 `actor_user_id`；数据库中不存在 `admin_accounts` 与 `users` 的身份映射字段、外键或映射表。

测试登录态准备必须使用密码登录接口 `/api/auth/password/login`，密码为手机号后六位。除专门验证短信验证码能力的测试外，禁止调用短信验证码申请、查询或验证接口。

## 11. 失败模式与回滚

| 失败模式 | 防护 | 回滚方式 |
| --- | --- | --- |
| 所有权回填错误 | 唯一映射校验、抽样核对、异常硬停止 | 保留旧列和映射表，按批次逆向恢复 |
| 新鉴权漏拦截 | 双读比对、跨用户负向测试 | 功能开关切回旧读路径，但禁止新旧双写分叉 |
| 队列仍有旧消息 | 消息版本监控、死信扫描 | 保留旧消费者至排空，重放失败消息 |
| 存储对象迁移缺失 | 校验和、对象数量与访问日志核对 | 旧键只读保留，恢复映射读取 |
| 大表迁移锁表 | 小批次、限速、超时和可恢复游标 | 停止批次，不回滚已验证批次 |
| 删列后才发现引用 | 零引用门禁、灰度期和完整保留周期 | 在 Drop 前回退应用；Drop 后只能执行向前修复迁移 |

不可逆操作必须放在最后。回滚能力以“旧列仍在、旧表仍在、旧对象仍可读”为边界；进入 Drop 阶段前必须取得数据校验和运行时零命中的共同证明。

## 12. 并行实施泳道

1. **数据库泳道：** 清单、目标列、回填、索引、约束、删列删表。
2. **后端泳道：** ActorContext、鉴权、服务查询、任务与事件、后台接口。
3. **契约与前端泳道：** DTO、API 客户端、状态管理、缓存、本地存储和 UI 文案。
4. **基础设施泳道：** 对象存储、队列、缓存键、监控与数据核对工具。
5. **质量泳道：** 迁移测试、跨用户隔离、异步排空、性能基线和零引用扫描。

各泳道可以并行开发，但发布顺序必须遵循 Expand → Backfill → Cutover → Drain → Contract/Drop。

## 13. 最终验收门槛

### 13.1 代码与契约零引用

`npm run check:user-scope-zero-refs` 必须在整个仓库通过。该门禁不设置历史迁移、测试、文档或生成物白名单，仅排除 `.git` 与 `node_modules`，并同时检查两类旧 ID 的 snake_case 与 camelCase 形式。

同时确认没有用通用 scope 字段伪装旧边界、默认租户 UUID 或兼容作用域生成器。

### 13.2 数据库零引用

- `information_schema.columns` 中无旧列；
- `pg_constraint`、`pg_indexes`、`pg_views`、`pg_matviews`、`pg_proc`、触发器和 RLS policy 中无旧引用；
- 废弃表不存在；
- 全部业务记录可唯一归属到用户、项目、团队成员分配或明确的系统级语义；
- 孤儿记录、多候选归属和迁移异常均为零。

### 13.3 运行时零依赖

- API 不接受也不返回旧字段；
- 队列、Outbox、缓存、本地存储、对象键和日志标签不再生成旧字段；
- 旧格式读取和兼容消费者命中连续一个完整保留周期为零；
- 主用户与子用户的授权回归通过，跨用户隔离测试通过。
- 前台管理员始终按真实用户授权；后台管理员始终按独立后台账号授权，二者幂等键与审计主体不可混用。

## 14. 可复用基础

本次改造不重新发明用户、团队和积分模型。当前 schema baseline 中的项目、用户、团队成员、用户钱包及分配关系是目标模型承载点；模型目录静态数据由独立 reference seed 提供。

复用不等于直接沿用所有旧字段。每个候选表仍需检查是否暗含组织/工作空间边界、复合唯一约束或兼容逻辑。

## 15. 实施约束

- 每个改动批次只处理一个明确数据域，避免跨域重构。
- 不猜测历史业务归属；无法确定的记录必须报告并人工决策。
- 数据库连接和验证必须使用项目 `.env` 中正式的 `DATABASE_URL`，不得替换为猜测值或 `TEST_DATABASE_URL`，且不得输出凭据。
- 先增加目标结构并验证，再删除旧结构；禁止在同一不可观察步骤中完成回填和删列。
- 每个阶段都应产出可复查的记录数、异常数、性能数据和回滚点。

## 17. 完成定义

只有同时满足以下条件，才能宣布去组织/去工作空间改造完成：

2. 所有业务数据完成确定性归属，异常为零。

5. 旧表、旧列、旧索引、旧约束和兼容代码已经删除。
6. 全仓与数据库零引用门禁通过。
7. 主用户、子用户、跨用户隔离和核心业务回归全部通过。
8. 前台管理员用户身份与后台管理员独立身份的数据库、认证、授权、幂等和审计隔离测试全部通过。
