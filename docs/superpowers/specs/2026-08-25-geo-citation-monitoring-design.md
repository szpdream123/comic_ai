# GEO 引用监测机制设计

## 目标

在现有 GEO 运营页面补齐可审计的引用监测能力。系统不声称知道大模型内部是否已经“收录”某篇文章，只记录一次真实问答快照能否观察到灵曦AI品牌提及或官网文章引用。

## 已确认方案

采用混合采集：

- 有合规官方 API 且后台已配置对应文本模型的平台，可以自动提问。
- 没有稳定官方查询接口的平台，由超级管理员粘贴原始回答并导入。
- 禁止绕过验证码、登录限制或反爬机制抓取第三方消费者网页。
- 自动与人工结果必须标明来源，不能混为同一种证据。

比较过但不采用的方案：

1. 纯 API：自动化程度高，但无法覆盖夸克、秘塔、纳米等无可用查询 API 的平台。
2. 浏览器自动化：看起来覆盖最广，但登录、验证码、页面变化和平台条款会导致结果不稳定且不可持续。
3. 混合模式：自动覆盖合规平台，人工补齐其余平台，证据边界最清楚，因此采用。

## 用户体验

GEO 运营页增加“引用监测”区域：

- 选择一篇已发布内容。
- 选择目标平台。
- 官方 API 平台选择对应模型后执行自动检测。
- 其他平台逐题粘贴原始回答后导入。
- 历史结果按时间倒序展示平台、来源、文章版本、判定汇总和检测时间，并可展开复核逐题回答与引用链接。
- 已完成回答的判定只使用三种状态：`not_mentioned`、`mentioned`、`cited`；尚未执行由“无监测记录”表达，不写入伪结果。

页面文案必须说明：“引用监测反映一次回答快照，不代表平台内部索引状态。”

## 数据模型

### `geo_monitor_runs`

一次内容、平台和来源明确的监测批次：

- `content_item_id`：必须指向已发布内容。
- `content_version_id`：绑定监测开始时的当前发布版本，后续重新发布不会让旧结果冒充新版本。
- `platform_id`：复用 `geo-platforms.ts` 的稳定平台 ID。
- `source_type`：`official_api` 或 `manual_import`。
- `status`：`running`、`succeeded` 或 `failed`。
- `model_code`：仅官方 API 运行需要。
- 保存操作者、错误摘要和起止时间。

### `geo_monitor_results`

每个问题一条不可变问答快照：

- 保存运行、问题、原始问题、原始回答、引用 URL、模型网关请求编号和创建时间。
- 保存派生分析：品牌是否提及、是否引用当前官网文章、状态和分析规则版本。
- 原始问题、原始回答和原始引用 URL 不允许修改或删除。
- 同一运行和问题只能有一条结果。

现有 `geo_questions.last_monitored_at` 在结果成功写入后更新。现有 `coverage_status` 继续只表示内容生产覆盖，不改变含义。

## 判定规则

分析使用确定性代码，不让另一个模型裁决是否命中：

1. 将“灵曦AI”“灵曦 AI”按空白和大小写归一化后检查品牌提及。
2. 从回答正文和导入的引用字段合并提取 `http`/`https` URL，去重并保留原值。
3. 将 URL 的规范化来源（协议、域名、端口）及路径与当前官网文章比较，二者都一致才为 `cited`。
4. 未引用文章但提到品牌为 `mentioned`。
5. 两者都没有为 `not_mentioned`。

引用命中优先级高于品牌提及。分析规则版本固定为 `geo-citation-v1`，未来可基于原始快照重算派生字段。

## 自动采集

自动运行复用 `TextModelGatewayService` 与后台模型配置，不新增模型 SDK。平台与提供商必须匹配：

- `deepseek` 接受提供商名 `deepseek`。
- `tongyi` 接受提供商名 `qwen`、`dashscope` 或 `aliyun-bailian`。

其余平台首版只允许人工导入。模型返回结构为 `{ "answer": string, "citedUrls": string[] }`，服务端严格解析。请求失败或输出格式无效时将运行标为 `failed`，不创建残缺结果。单次官方 API 运行最多处理 20 个关联问题，避免形成无界调用和费用。

## 接口

所有接口沿用 `/api/admin/geo/*` 和 `geoManage` 权限，仅允许 `super_admin`：

- `GET /api/admin/geo/monitoring?contentItemId=<uuid>`：返回当前发布内容与问题、带文章版本的运行和结果；平台能力沿用同页加载的 `GET /api/admin/geo/platforms`。
- `POST /api/admin/geo/monitoring/manual`：导入一个平台的一组问题回答。
- `POST /api/admin/geo/monitoring/official-api`：对一篇发布内容的关联问题执行官方 API 检测。

两个写接口继续要求 `idempotency-key`。请求只接受内容当前发布版本关联的问题，不能监测任意未关联问题。

## 失败处理

- 内容不存在或未发布：`404 geo_monitor_content_not_published`。
- 平台不存在：`400 geo_monitor_platform_invalid`。
- 自动化能力不可用：`400 geo_monitor_platform_manual_only`。
- 模型提供商与平台不匹配：`400 geo_monitor_model_platform_mismatch`。
- 手工导入缺题、重复题或空回答：`400 geo_monitor_manual_results_invalid`。
- 模型调用或输出解析失败：运行保留为 `failed`，返回可重试错误，不写结果。

## 测试

- 数据库测试覆盖表、约束、索引、不可变触发器和迁移注册。
- 单元测试覆盖 URL 提取、品牌归一化、文章路径匹配和三种结果判定。
- 服务测试覆盖人工成功、无效内容编号、自动成功、平台与模型不匹配、模型失败不留残缺结果、provider request 关联、发布版本切换和迟到结果 fencing。
- HTTP 测试覆盖监测权限、缺少及重放幂等键、无效内容编号、人工导入、列表和人工平台误用官方接口；官方模型成功与失败由服务层真实数据库测试覆盖。
- 后台 UI 测试覆盖免责声明、平台能力、人工导入、自动运行请求、历史详情、响应式布局和过期请求不覆盖当前状态。

## NOT in scope

- 定时任务和周期调度：首版由管理员手动触发，先验证信号质量。
- 持久化后台队列和失败问题续跑：首版官方 API 仍由管理员请求同步发起；已有问题数上限、心跳、断连取消和失败审计，批量/周期运行再升级为可续跑任务。
- 第三方消费者网页自动登录或抓取：合规性和稳定性不足。
- 搜索引擎爬虫收录检查：它与大模型回答引用是不同问题。
- 趋势图和跨周期同比：先积累可信历史数据，再增加分析视图。
- 自动发布或修改 GEO 文章：监测只读，不反向改内容。
